# Checkee 项目状态与设计准则

> 本文档是 Checkee 的产品理念、设计约束、架构边界与当前实现状态的共同基准。
>
> 进行 UI、UX、数据或功能改动前先阅读本文档；完成重大改动后同步更新相关章节与“最近检查”。本文档描述约束和现状，不是要求一次性重构的待办清单。

## 1. 产品概览

**产品名称：** Checkee  
**定位：** F-1 Check 时间线案例归档与观察平台。

目标是通过社区提交、审核并发布的案例，让用户理解真实世界的 F-1 处理时间线。核心价值是：

- 数据真实性与可追溯性；
- 清晰的信息层级；
- 克制且有明确目的的界面；
- 值得信任的展示。

## 2. 产品与交互原则

### 核心原则

如无必要，勿增实体。每个按钮、入口、视觉效果和动效都必须服务于明确的用户目的。

避免新增不必要的按钮、重复说明、无意义装饰、强烈边框、持续动效或游戏化界面。Hover 与选中状态优先通过轻微上移、柔和阴影、低饱和环境光和材质变化表达；不使用呼吸、闪烁或持续动画。

### 视觉方向

关键词：东方、雅致、克制、展厅、玉、墨、数据可信度。Checkee 应像东方档案展，而不是普通仪表盘。

默认中文正文使用仿宋系字体。`HYBlackMythU` / `heishenhua` 仅用于标题、分章文案与少量东方感强调，不应泛化到所有正文和控件。

## 3. 页面与数据架构

| 页面/系统          | 职责                                 | 当前主要实现                                     |
| ------------------ | ------------------------------------ | ------------------------------------------------ |
| `/`                | 名人堂：公开案例的荣誉展示与归档浏览 | `CheckmateExperience` 的 `HallOfFame`            |
| `/view`            | 五城 F-1 数据统计、趋势与案例浏览    | `CheckmateExperience` 的城市视图                 |
| `/about`           | 个人资料与联系入口                   | 独立 About 页面                                  |
| `/api/submissions` | 接收并校验用户投稿                   | 仅服务端写入 Supabase                            |
| `/admin`           | 内部审核投稿                         | 不进入公开导航或 sitemap                         |
| `/admin/hall`      | Hall 发布状态与 release 历史控制中心 | 只读本地发布文件，并查询 Supabase published 状态 |

公开名人堂只读取 `data/checkmate/hall-master.json` 中 `visibility = published` 的记录。用户投稿首先写入 Supabase 审核池，审核发布后经导出脚本冻结到 `published-submissions.json`，再合并生成带 `dataVersion` 的 `hall-master.json`，并将同一份数据保存到不可覆盖的 `data/checkmate/releases/YYYYMMDD-vXXX/`；页面不会直接读取 Supabase 或手工改写原始数据。

## Navigation

- Desktop and Mobile navigation share `HEADER_NAV_LINKS`.
- Do not maintain separate mobile labels.
- `/view` label: `统计`.

## 4. 名人堂信息架构（`/`）

```text
Hall
├── Top 3 荣誉展示
├── HallSectionDivider
├── Rank 4–10 精选展示
├── HallSectionDivider
└── Rank 11+ 档案列表（分页）
```

### Top 3：荣誉展示

Top 3 不是普通数据列表。当前规则：

- 三张等尺寸圆形玉质感卡片，分别为冠军暖玉、第二名青玉、第三名暖朱砂玉；
- 用色、位置、环境光和阴影建立层级，不添加皇冠、奖牌或吊挂装饰；
- 冠军只通过位置提升，不放大卡片；桌面端当前提升量约为卡片高度的二分之一（最近一次已确认的比例），移动端取消该提升以保证紧凑布局；
- 地点置顶；学位、专业、学校、日期合并为紧随地点的一行铭牌；主体名称以系统楷体置于圆心附近；等待天数位于底部居中；不展示名次编号角标；
- 控制入口只保留“提交案例”和“修改/说明”两个。

### Rank 4–10：精选展示

定位为 Featured Showcase：字体、间距和环境光强于档案列表，但不能复制 Top 3 圆形卡片，也不能压过 Top 3。

### Rank 11+：档案列表

定位为高效浏览的数据归档：较小间距、较弱阴影和较低对比度，使用分页控制密度。

### HallSectionDivider

分隔符代表展厅章节转换，不是普通横线。保持 `HYBlackMythU`、墨色至暖灰至玉白的渐变文字、柔和文字阴影和淡出线条；除非明确要求，不重做其文字或样式。

基准文案：

```text
Top 3 → 4–10
但愿人长久，千里共Check娟。

4–10 → 11+
曲径通幽处，Check房花木深。
```

## 5. 数据展示规则

这些是展示层规范，不修改原始事实数据。

- `Master`、`master`、`MASTER` 显示为 `Ms`；其他学位保持原样。
- `AP`、`ap`、`Approved`、`approved` 统一显示为 `AP`。
- 已完成、AP、Issued 使用低饱和绿/玉感；`Refused` 使用低饱和朱砂红；等待中保持中性。
- 等待天数是 release 的派生值：有 `endDate` 时为 `endDate - startDate`，否则为固定 `snapshotDate - startDate`；不得使用 Excel 缓存值、系统时间、浏览器日期或 build 当日日期。
- 状态颜色只影响展示，不得改写来源数据。

## 6. 数据发布边界

- `visibility` 描述是否可进入名人堂；`review_status` 仍描述投稿审核记录状态，两者不能互相替代。
- 从 `pending` 发布为 `published` 时，由数据库触发器写入 `published_at`。
- `hall-master.json` 是生成产物，不手工编辑；历史数据来源标为 `legacy_excel`，用户投稿标为 `submission_user`。
- 每次正式导出都创建新的 release 目录，版本格式为 `YYYYMMDD-vXXX`；release 内保存 Hall、published submissions 与 `release-meta.json`，历史版本不自动删除或覆盖。
- 维护数据时使用 `scripts/convert-checkee-data.py`、`scripts/export-hall-master.py` 与 `scripts/verify-hall-data.py`，并检查来源、可见性、日期、等待天数派生规则、重复 ID 与历史记录一致性。

## 7. 受保护区域

以下区域仅在必要且明确授权时修改，并在改动后更新本文档：

- Top 3 结构、尺寸关系和控制入口；
- HallSectionDivider；
- `/about` 与 `/view` 的既有信息架构；
- Hall 数据 schema、可见性规则与排名逻辑；
- 审核、发布与静态快照的数据链路。

## 8. 开发约定

1. 改动前阅读本文档及受影响组件；优先复用既有组件、CSS 变量和设计 token。
2. 不为简单展示重复造组件、引入无必要抽象、魔法数字或内联样式。
3. UI 改动要兼顾深色模式、移动端、键盘焦点与减少动态效果偏好。
4. 数据改动需区分展示数据、审核池和发布数据，禁止通过前端直接修改来源数据。
5. 重大改动完成后更新“页面与数据架构”“受保护区域”或“最近检查”中受影响的内容。

建议验证顺序：

```bash
pnpm lint
pnpm typecheck
pnpm build
git diff --check
```

## 9. 当前状态

已具备：

- Top 3 圆形玉质感荣誉展示及响应式布局；
- 两个名人堂控制入口：案例投稿、数据说明/修改反馈；
- Rank 4–10 精选展示与 Rank 11+ 分页档案列表；
- 状态展示归一化、数据说明与反馈整合；
- Supabase 投稿审核、发布状态与 Hall 静态主数据导出/校验链路；
- Hall 发布版本目录、`dataVersion` 与最新 release 一致性校验；
- `/admin/hall` Hall 发布控制中心，可查看当前状态、release 历史和待发布提示；
- `/admin/submissions` 审核详情包含完整案例上下文、Created/Reviewed 时间与 approve/reject 成功反馈；
- `/view` 五城统计、初始/无匹配空状态及移动端适配；
- “修改/说明”先确认诉求，再提供对应说明与邮件草稿准备后的预期管理。

后续优先级：可用性、数据可信度、性能与无障碍；避免只为视觉而新增内容或动效。
